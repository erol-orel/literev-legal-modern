## Project

The top-level entity representing a user's analysis session. One project = one Elasticsearch query + one clustering run.

| Field | Type | Notes |
|---|---|---|
| `user` | FK → User | nullable — allows anonymous or shared projects |
| `name` | CharField(256) | human-readable session name |
| `creation_date` | DateField | auto-set on creation |
| `query` | CharField(4096) | Boolean search query sent to Elasticsearch |
| `natural_language_query` | CharField | nullable — original user intent before NL→Boolean conversion |
| `range_begin_date` | DateField | document date filter start |
| `range_end_date` | DateField | document date filter end |
| `total_documents` | IntegerField | count of documents retrieved from ES |
| `selected_indices` | JSONField | indices of documents selected after refinement |
| `step` | CharField | current pipeline step label (e.g. `"clustering"`, `"done"`) |
| `step_number` | IntegerField | numeric step index for progress tracking |
| `is_finish` | BooleanField | whether pipeline has completed |
| `is_running` | BooleanField | whether a background task is active |
| `best_dbcv` | FloatField | best DBCV score from Optuna clustering optimization |
| `actual_task_code` | CharField | nullable — Celery task ID for progress polling |

**Usage patterns:**
- Check `is_running` before starting a new pipeline task
- `step` / `step_number` drive progress UI
- `best_dbcv` reflects clustering quality (higher = better separated clusters)
- `selected_indices` is written after the user completes refinement iterations

## Document

A single legal document retrieved from Elasticsearch and stored locally for NLP processing.

| Field | Type | Notes |
|---|---|---|
| `project` | FK → Project | |
| `chamber` | CharField | court chamber identifier (`coll_nom`) |
| `record_key` | CharField | unique corpus ID (stable across projects) |
| `decision_type` | CharField | type of decision |
| `procedure_type` | CharField | procedure category |
| `decision_date` | DateField | date of judicial decision |
| `procedure_year` | DateField | year of procedure |
| `descriptors` | TextField | keyword descriptors |
| `standards` | CharField | legal standards/norms cited |
| `result` | TextField | decision result summary |
| `raw_document_id` | TextField | Elasticsearch `_id` |
| `raw_document_text` | TextField | full plain text from ES |
| `document_html_text` | TextField | HTML-formatted version |
| `prepared_for_ngrams` | TextField | intermediate form after normalization |
| `preprocessed_document` | TextField | final cleaned/lemmatized form used for TF-IDF |

**Lifecycle:**
1. Created by `pipeline.create_document_db()` after ES collection
2. `raw_document_text` is populated immediately
3. `preprocessed_document` is filled after `literev_core.preprocessing` runs
4. `prepared_for_ngrams` holds intermediate spacy output

**Key note:** `record_key` is the stable identifier linking back to the Elasticsearch corpus. Use this when cross-referencing documents across projects.

## Cluster

A group of semantically similar documents, produced by the HDBSCAN clustering step.

| Field | Type | Notes |
|---|---|---|
| `project` | FK → Project | |
| `order` | IntegerField | display order (sorted by cluster size or quality) |
| `topic` | CharField(8196) | LLM-generated topic label for the cluster |
| `summary` | TextField | LLM-generated summary of the cluster's documents |

**Notes:**
- HDBSCAN may produce a noise cluster (label -1) — these are documents that don't belong to any cluster
- `topic` and `summary` are generated by `nlp.get_cluster_summary()` / `nlp.nlp_topic_description()` using the top-10 most representative documents
- `order` is filled by the `fill_order_cluster` management command if not set during creation

## ClusterElement

Stores the 2D PaCMAP projection coordinates for each document, enabling visualization and nearest-neighbor lookup.

| Field | Type | Notes |
|---|---|---|
| `pos_x` | FloatField | X coordinate from PaCMAP 2D projection |
| `pos_y` | FloatField | Y coordinate from PaCMAP 2D projection |
| `document` | FK → Document | |
| `cluster` | FK → Cluster | the cluster this element belongs to |

**Usage:**
- `table_choice.neighbour_document()` uses `pos_x`/`pos_y` to find the 10 nearest documents in 2D space using Euclidean distance
- Visualization frontend reads these coordinates to render the cluster scatter plot

## TableChoice

Tracks the display status and user selection state for each document in a project. One record per (user, project, document) triple.

| Field | Type | Notes |
|---|---|---|
| `user` | FK → User | |
| `project` | FK → Project | |
| `document` | FK → Document | |
| `to_display` | BooleanField | whether this doc appears in the current view |
| `is_initial` | BooleanField | whether this is the original (pre-refinement) document set |
| `is_check` | BooleanField (nullable) | `True`=YES, `False`=NO, `None`=MAYBE/unselected |

**Selection states:**
- `is_check=True` — user confirmed this document is relevant
- `is_check=False` — user excluded this document
- `is_check=None` — not yet decided (default)

**`to_display`** controls which docs are visible. After neighbor expansion, newly added documents have `to_display=True` but `is_initial=False`.

## ProjectRefinement

An iterative refinement workflow attached to a project. Users can create multiple refinements (e.g. one per research question) on the same project.

| Field | Type | Notes |
|---|---|---|
| `project` | FK → Project | |
| `owner` | FK → User | |
| `name` | CharField | refinement label |
| `origin` | FK → ProjectRefinement (nullable) | self-referential — allows branching refinement trees |
| `filters` | JSONField | structured filter criteria applied to this refinement |

## RefinementIteration

One iteration within a refinement workflow. Each iteration captures a snapshot of which documents were checked, excluded, or newly added as neighbors.

| Field | Type | Notes |
|---|---|---|
| `refinement` | FK → ProjectRefinement | |
| `parent_iteration` | FK → RefinementIteration (nullable) | forms a linked list of iterations |
| `number_documents` | IntegerField | total documents in this iteration |
| `checked_documents_ids` | JSONField | list of document IDs marked YES |
| `excluded_documents_ids` | JSONField | list of document IDs marked NO |
| `new_neighbors_ids` | JSONField | document IDs added via neighbor expansion |
| `result_documents_ids` | JSONField | final document IDs for this iteration |

**Iteration flow:**
```
Iteration 1: user marks docs YES/NO
        │
        ▼
iterate_check_list() → finds neighbors of YES docs
        │
        ▼
Iteration 2: new neighbors added, user marks again
        │
        ▼
... repeat until satisfied
```

## ProjectRAG

One RAG (Retrieval-Augmented Generation) execution — a user question answered against a document subset.

| Field | Type | Notes |
|---|---|---|
| `project` | FK → Project | |
| `query` | CharField(500) | the question posed by the user |
| `created_at` | DateTimeField | auto-set |
| `status` | CharField | see status values below |
| `summary_answer` | TextField (nullable) | LLM-generated overall summary |
| `num_documents` | PositiveIntegerField | number of documents processed |
| `valid_answer_count` | PositiveIntegerField | documents with a valid (non-empty) answer |

**Status values:**

| Status | Meaning |
|---|---|
| `in_progress` | RAG task is queued or running |
| `questioning_documents` | per-document LLM answers being generated |
| `generating_scores` | faithfulness scores being computed |
| `generating_summary` | overall summary being generated |
| `generating_statistics` | classification stats being computed |
| `tagging_considerations` | considerations being tagged |
| `completed` | all steps finished successfully |
| `failed` | an error occurred — check Sentry / logs |

## ProjectDocumentRAG

One LLM answer for a single document within a RAG run.

| Field | Type | Notes |
|---|---|---|
| `project_rag` | FK → ProjectRAG | |
| `document` | FK → Document | |
| `citation` | TextField | extracted verbatim quote from the document |
| `citation_context` | JSONField | surrounding context for the citation |
| `answer` | TextField | LLM-generated answer for this document |
| `confidence_score` | FloatField (nullable) | ragas faithfulness score (0.0–1.0) |

**Notes:**
- `citation` is extracted using `rapidfuzz` fuzzy matching against the raw document text
- `confidence_score=0.0` indicates an invalid/empty answer (not a low-confidence valid answer)
- `citation_context` is a JSON dict with chunk text and position information

## ProjectRAGStats

Stores classification statistics for closed-ended (yes/no/maybe) RAG questions. One record per `ProjectRAG`.

| Field | Type | Notes |
|---|---|---|
| `project_rag` | OneToOneField → ProjectRAG | |
| `classification_stats` | JSONField | dict of label → count/percentage |
| `user` | FK → User (nullable) | |
| `created_at` | DateTimeField | |

**`classification_stats` structure (example):**
```json
{
  "yes": {"count": 12, "percentage": 0.60},
  "no":  {"count": 6,  "percentage": 0.30},
  "maybe": {"count": 2, "percentage": 0.10}
}
```

## Migration Strategy

- All schema changes must go through Django migrations — never edit the database directly
- Generate migrations: `makim django.makemigrations`
- Apply migrations: `makim django.migrate`
- Migration files live in `src/literev/migrations/` and are committed to git
- Data migrations (for backfilling new fields) should use `RunPython` with a reverse function

## Indexes and Performance

Key query patterns and recommended indexes:

| Query | Fields to index |
|---|---|
| Documents by project | `Document.project` (auto via FK) |
| TableChoice per user+project | `(user, project)` composite |
| ClusterElement by cluster | `ClusterElement.cluster` (auto via FK) |
| ProjectDocumentRAG by project_rag | `ProjectDocumentRAG.project_rag` (auto via FK) |
| ProjectRAG status polling | `ProjectRAG.status` |

Add explicit `db_index=True` on `ProjectRAG.status` if polling queries are slow.
